# H2H 与全对 Dijkstra 初版对比实验设计

## 1. 实验目标

在相同路网、相同实例和相同 MA-FSTSP 参数下，对比两种**卡车距离后端**：

- `APD-Eager`：使用 NetworkX 全对 Dijkstra 物化卡车距离；
- `H2H`：构建或加载 H2H 索引，按需查询精确卡车距离。

两组都使用当前统一的按需 haversine 无人机距离。实验回答：

1. 两种后端是否返回等价的最短路和 MA-FSTSP 目标值；
2. 冷距离准备、热标量查询和端到端时间有何差异；
3. 随着共享同一距离后端的实例数增加，预处理成本如何被摊销。

本实验不是论文严格复现，也不比较无人机距离物化策略。

## 2. 初版范围

| 名称 | 文件 | 节点数 | 仓库 | 客户 | 每车无人机 |
|---|---|---:|---:|---:|---:|
| NYC-1K | `datasets/nyc_1024.graphml` | 1,024 | 5 | 50 | 3 |
| NYC-11K | `datasets/nyc_11000.graphml` | 11,000 | 10 | 50 | 4 |

统一参数：

- 随机种子：`0`；
- 无人机航程：`1.5 km`；
- 无人机/卡车速度比：`1.6`；
- `theta=(0.5, 0.5)`；
- 实例批量：`N=1、10、100`；较小批量始终取同一批 100 个实例的前缀。

初版不包含 Boston-8K、不统计峰值内存，也不测试 `auto` 或 `query_batch()`。

## 3. 后端定义

### 3.1 APD-Eager

卡车距离必须从零执行：

```python
dict(nx.all_pairs_dijkstra_path_length(graph, weight="weight"))
```

可通过 `EagerDistanceMatrix.from_graph()` 获得相同语义。基准脚本直接调用该类，避免生产配置中的 1,000 节点保护改变实验含义；不修改生产代码。

### 3.2 H2H

- `H2H-Cold`：使用空的临时索引目录，从零完成图规范化、索引构建、校验和首次打开；
- `H2H-Warm`：使用已经校验且图哈希匹配的索引，只测加载、首次打开及后续查询。

冷构建不得复用 `datasets/indexes/` 中的既有索引，也不得删除既有索引。

## 4. 测量项目

### 4.1 冷距离准备时间

计时起点：GraphML 已加载并标准化完成。公共的地图读取时间不计入。

计时终点：后端已能返回距离。H2H 必须执行一次固定查询以强制完成 DLL 加载和 mmap 打开。

分别记录：

- `APD-Eager prepare`；
- `H2H-Cold prepare`；
- `H2H-Warm load`。

每次冷测试使用独立进程；H2H-Cold 每次使用新的空临时目录。

### 4.2 热标量查询时间

后端准备完成后，先执行 1,000 次不计时预热，再查询固定生成的 100,000 个有向节点对：

```python
distance["truck"][source][target]
```

节点对在两种后端中完全相同，生成节点对和计算正确性不计入查询时间。保存查询结果校验和，防止测试循环未真正消费结果。

### 4.3 端到端时间

对每个 `N=1、10、100` 分别测量：

```text
冷端到端时间 = 后端冷准备 + N 个模型的构造与求解
热求解时间   = 后端准备完成后，N 个模型的构造与求解
```

GraphML 加载和固定实例生成均在计时前完成。每个批量只准备一次距离后端，随后由全部实例共享。

## 5. 公平性控制

- 不使用 `auto`，显式选择 APD-Eager 或 H2H；
- 两组使用同一标准化图、边方向、`weight` 和图哈希；
- 两组使用完全相同的仓库、客户、参数和实例顺序；
- 单进程、单 worker 运行，避免并行度掩盖后端差异；
- 记录 Python、NetworkX、操作系统、CPU 和 Git 提交；
- 同一项目在相近系统负载下运行，不交叉并发两个后端；
- 每项独立重复 3 次，报告中位数，同时保留全部原始结果。

## 6. 正确性要求

性能结果只有在以下检查通过后才有效：

1. 固定节点对上的 H2H 与 Dijkstra 距离满足 `rel_tol=1e-12, abs_tol=1e-12`；
2. 同一 MA-FSTSP 实例的目标值满足 `rel_tol=1e-9, abs_tol=1e-9`；
3. 路线允许因并列最优和浮点加法顺序不同而不完全相同，但必须通过路线可行性检查；
4. 任何距离或目标值不一致都单独报告，不能计入性能结论。

## 7. 失败与结果记录

NYC-11K 的 APD-Eager 如果出现超时、`MemoryError` 或进程被系统终止，应记录实际状态，不虚构耗时，也不阻止 H2H 测试继续执行。初版不测量具体内存值。

每条原始结果至少包含：

```text
dataset, backend, cache_state, test_kind, instance_count,
repeat, elapsed_seconds, status, max_distance_error, max_objective_error
```

建议同时输出 CSV 和 JSON；汇总表使用 3 次重复的中位数。

## 8. 结果解释边界

- 冷准备更快：说明该后端建立可查询距离结构更快；
- 热查询更快：只说明当前标量接口更快；
- 冷端到端更快：说明在给定实例批量下具有实际总时间优势；
- H2H 热标量查询即使慢于字典查询，也不否定其在冷准备和大图可用性方面的价值；
- 结论只适用于 NYC-1K 和 NYC-11K，不表述为所有小图或所有道路网络都更快。

## 9. 推荐执行顺序

1. 正确性检查；
2. NYC-1K 冷准备与热查询；
3. NYC-1K 端到端 `N=1、10、100`；
4. NYC-11K 冷准备与热查询；
5. NYC-11K 端到端 `N=1、10、100`；
6. 汇总原始结果、中位数、失败状态和结论边界。
